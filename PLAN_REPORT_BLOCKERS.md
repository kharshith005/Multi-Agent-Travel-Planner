# Report-Blocker Fixes — Implementation Plan

Five issues surfaced in the latest validation sweep that must be resolved before the final report numbers can be regenerated by `python -m eval.run_eval --split validation --system all`:

1. Claude Haiku 4.5 — Vertex 429 quota exhaustion on `us-east5`.
2. Gemini 2.0 Flash-Lite — Vertex 404 (model not GA in `us-central1` for this project).
3. `Intent.cuisine` Pydantic `string_type` error when the parser returns a list.
4. SerpAPI round-trip reads a non-existent `return_flights` field instead of using `departure_token`.
5. `eval/constraints.py` rule set diverges from TravelPlanner Table 1 / Table 4.

Issues 1–3 block the eval from running. Issue 5 makes the numbers non-comparable to paper Table 3. Issue 4 affects only `app.py` UX, not eval.

## Phase 5 — Parallelize transport specialist (post-report optimization)

**Goal.** Run the transport specialist in parallel with lodging/dining/sightseeing instead of strictly before them, without paying repair-loop cost.

**Why it isn't free today.** Transport's output is the source of `trip_windows` (`coordinator.py:284-310`, `_merge_trip_windows`). Lodging/dining/sightseeing each call `format_trip_windows(ctx)` (`rules.py:124`) to build a YES/NO grid in their prompts (no Day-1 lunch when arrival ≥14:30, no last-day breakfast when departure <09:00, etc.). If we naively parallelize, those grids are absent and every late-arrival or early-departure query fails timing rules and trips repair — adding LLM calls (1 per affected specialist per round, up to `REPAIR_MAX_ROUNDS=3`). Wall-time saving (~0.5–1 s) gets dwarfed by token spend.

**Approach: derive `trip_windows` in the research node, then fan out all 4 in parallel.** `tools/live_apis.py` already returns flight strings with explicit `HH:MM->HH:MM`; `eval/run_eval.py:_sandbox_tool_context` (lines 87–97) does the same. The first outbound flight's arrival time and the first return flight's departure time are fully deterministic from prefetched data — the transport LLM call today just *picks* among pre-ranked options. So we can populate `trip_windows` before any specialist runs.

**Files**
- `agents/coordinator.py` — research node, LangGraph wiring.
- `eval/run_eval.py` — mirror in `_sandbox_tool_context` so eval and live paths stay aligned (the canonical contract from `CLAUDE.md` §Architecture).

**Changes**

1. In the research node, after `flights_outbound` / `flights_return` are populated:
   - parse `flights_outbound[0]` with the existing `_extract_arrival_minutes` → `arrival_minutes_day1`
   - parse `flights_return[0]` with `_extract_departure_minutes` → `departure_minutes_last`
   - write `ctx["trip_windows"]` using the same `TripWindows` shape `_merge_trip_windows` produces today
   - skip cleanly when no flights are present (driving/taxi-only) — leave `trip_windows` unset, matching today's pre-transport state.
2. Mirror the population in `eval/run_eval.py:_sandbox_tool_context`.
3. Switch LangGraph edges in `coordinator.py`: replace `research → transport → fan-out` with `research → [transport, lodging, dining, sightseeing]` parallel.
4. Drop the redundant `_merge_trip_windows` calls at `coordinator.py:680,686`. **Keep the function itself** — repurpose it as a reconciliation step: if transport's chosen flight differs from the research-derived window by >30 min, re-route lodging/dining/sightseeing through repair. Cheap insurance for the edge case where transport's pick deviates from `flights_outbound[0]`.
5. Leave the post-assembly safety clamp `_apply_timing_adjustments` (`coordinator.py:331-392`) as-is — it's orthogonal defense-in-depth.

**Validation**
- `python -m eval.run_eval --split validation --system multi --limit 30` before vs. after. Expect:
  - `final_pass` unchanged (timing context preserved upstream)
  - `latency_seconds` per row down by ~one specialist call's wall time
  - `avg_llm_calls` flat or marginally lower (fewer repair rounds on timing-edge queries)
- Spot-check 3 late-arrival queries: confirm the dining specialist's prompt receives a populated YES/NO grid.

**Risks**
- Window drift if `_rank_flight_options` is later changed so `[0]` isn't transport's most likely pick. Mitigation: the reconciliation step in (4) catches it.
- Driving-only trips have no `flights_outbound` — `trip_windows` stays unset, specialists run grid-less. Same as today's first-call behavior; no regression.

**Time.** ~45 min including the comparison eval run.

**Why this is post-report.** Phases 1–3 are correctness fixes that unblock the report numbers. Phase 5 is a latency / architecture optimization that changes the system diagram. Lock the numbers first, then optimize.

## Phase 10 — Morning departure filter via SerpAPI `outbound_times` + clamp tightening (Issue 1)

**Goal.** Push the time-of-day preference down to the SerpAPI request so the candidate pool is narrower and more relevant: prefer morning outbound (so Day 1 has time for activities) and afternoon/evening return (so last day has at least lunch / breakfast). Pair with cleaner Day-1 night-arrival handling and a clear surfacing of fixed budget ratios in each specialist's prompt.

**SerpAPI capability.** Per https://serpapi.com/google-flights-api, `outbound_times` accepts `"start,end"` (or `"out_start,out_end,ret_start,ret_end"` for round-trip) where each value is an hour 0–23. The filter is server-side, so it shrinks the response payload and reduces our local ranking work.

**Files**
- `tools/live_apis.py` — `flight_search` and `flight_search_round_trip`: pass `outbound_times` based on `prefer_early_departure` / `prefer_late_return`.
- `agents/coordinator.py` — `research_node`: pass `prefer_early_departure=True` (already does for one-way; confirm for round-trip).
- `agents/transport.py`, `agents/lodging.py`, `agents/dining.py`, `agents/sightseeing.py` — prompt: surface `category_caps` (the fixed 45/35/20 ratios from `agents/budget.py:48-50`) explicitly so each specialist sees its own cap.
- `agents/coordinator.py` — `_apply_timing_adjustments`: rely on `format_trip_windows` YES/NO grid being respected upstream; keep the clamp as defense-in-depth but neutralized to `"-"` (handled in Phase 7).

**Changes**

1. **`outbound_times` parameter** (one-way and round-trip):
   - `prefer_early_departure=True` → `outbound_times="4,12"` (4 AM – noon).
   - `prefer_late_departure=True` (one-way return) → `outbound_times="14,21"` (2 PM – 9 PM).
   - Round-trip (`type=1`): pass `outbound_times="4,12,14,21"` so call 1 narrows outbound by morning AND the implicit return preference is signaled. Call 2 (with `departure_token`) does not need the param — it's already paired.
   - On 0-result responses to a tight window, retry once without the filter and emit `on_progress("⚠️ no flights matched morning window — broadening")`.
2. **Specialist prompts surface fixed ratios.** Each specialist already reads `ctx["category_caps"]` for its category. Add a one-line statement in the SYSTEM prompt: e.g. transport: "Your category cap is ${transport_cap} ({transport_pct}% of trip budget). Stay at or under this — the budget agent enforces it strictly." Same template for lodging (35%) and dining (20%). Pull the formatting helper from `agents/rules.py`.
3. **Day-1 night-arrival handling** is already covered by the YES/NO grid (`format_trip_windows` in `rules.py:124-186`) and tightened by Phase 7's clamp ("-", not echoed time strings). No new logic needed here, but verify the grid thresholds in `rules.py:113-115` match the user's expectations:
   - `THRESH_D1_LUNCH_NO = 14:00`
   - `THRESH_D1_DINNER_NO = 19:00`
   - `THRESH_D1_ATTRACTION_NO = 16:00`

   These are correct for the paper's commonsense rule. Document them in the plan, do not change.

**Validation**
- One live `app.py` query — watch SerpAPI dashboard for `outbound_times=4,12` in the request URL.
- Compare the candidate count before/after on a same-day query: expect a smaller pool with better morning bias, no early-morning red-eyes vanishing.
- Eval sweep: `python -m eval.run_eval --split validation --system multi --limit 30` — `final_pass` should improve marginally (less timing-related repair); `avg_llm_calls` flat or down.
- Sanity: a query where there are NO morning options (e.g., very short notice) — confirm the broadening retry fires and a plan is produced.

**Risks**
- Server-side filter may exclude a valid 12:30 flight at the edge. Use `outbound_times="4,13"` (4–1 PM, one-hour buffer) if too aggressive.
- The retry path adds a SerpAPI call when the filter is too tight. Acceptable — it only fires when the first call returned nothing.

**Time.** ~45 min.

## Phase 12 — Lodging: airport-radius geo search + budget filter (Issue 2)

**Goal.** Replace today's broad text search ("hotels in {dest}") with a geo-radius nearby search around the destination airport (~30 mi), filtered to the lodging budget tier. This both narrows the pool to relevant options and respects the fixed 35% lodging cap from `agents/budget.py`.

**Today.**
- `coordinator.py:629`: `live.search_places(intent.dest, "hotels", max_results=n_hotels)` does a free-text Google Places search anchored on city name only.
- `tools/live_apis.py:114`: `search_places(city, query, *, max_results)` calls `googlemaps.Client.places(f"{query} in {city}")`. No radius, no price filter, no airport anchoring.
- `lodging_cost_targets` (price_level → est nightly $) is computed in `agents/budget.py:derive_lodging_targets` and surfaced to the lodging specialist's prompt — but only as text, not used to filter the candidate pool.

**Files**
- `tools/live_apis.py` — add `search_lodging_near(latlng, *, radius_m, max_results)` using `places_nearby`; extend airport resolution to also return lat/lng.
- `agents/coordinator.py` — `research_node`: prefer the geo search when destination airport is resolved; filter results by budget tier before storing in `ToolContext`.

**Changes**

1. **Airport coordinates.** `_resolve_with_fallback` already loads `airportsdata` to find the nearest IATA. Extend its return tuple to include `(lat, lon)` for the resolved airport (or for the user's geocoded destination when there's no airport fallback). Touch points:
   - `tools/live_apis.py:_resolve_with_fallback` — return `(iata, fallback_city, drive_leg, lat, lon)` (5-tuple).
   - All call sites in `coordinator.py:research_node` — unpack the new fields.

2. **Geo-radius lodging search.** Add to `LiveTravelAPIs`:
   ```python
   def search_lodging_near(
       self, latlng: tuple[float, float], *,
       radius_m: int = 48000,         # ~30 mi
       max_results: int = 20,
       budget_levels: set[int] | None = None,  # e.g., {1, 2} for ≤level 2
   ) -> list[dict]:
       payload = self._client().places_nearby(
           location=latlng, radius=radius_m, type="lodging",
       )
       rows = payload.get("results") or []
       out = []
       for r in rows[:max_results * 2]:  # over-fetch to allow budget filter
           level = r.get("price_level")
           if budget_levels and level is not None and level not in budget_levels:
               continue
           out.append({
               "name": r.get("name"),
               "address": r.get("vicinity") or r.get("formatted_address"),
               "rating": r.get("rating"),
               "price_level": level,
               "lat": r["geometry"]["location"]["lat"],
               "lon": r["geometry"]["location"]["lng"],
           })
       # Sort by rating desc, then price level asc (cheaper first within tier).
       out.sort(key=lambda h: (-(h.get("rating") or 0), h.get("price_level") or 99))
       return out[:max_results]
   ```

3. **Budget-tier selection.** Compute the `budget_levels` set from `lodging_cost_targets`. The lodging cap divided by `intent.days - 1` gives a target per-night cost; map that back to a price_level via the inverse of `_price_to_level` (which already lives in `eval/run_eval.py`). Move that helper to a shared spot (`agents/budget.py:price_level_for_nightly`) and import from both.

4. **`research_node` integration.**
   ```python
   dest_latlng = (dest_lat, dest_lon)  # from extended _resolve_with_fallback
   target_levels = budget.price_levels_for_nightly_target(...)
   try:
       hotels = live.search_lodging_near(dest_latlng, budget_levels=target_levels, max_results=n_hotels)
   except Exception:
       hotels = []
   if not hotels:
       # Fall back to today's text search ONLY if airport-radius search returned empty
       hotels = live.search_places(intent.dest, "hotels", max_results=n_hotels)
   ctx["hotels"] = hotels
   ```

5. **No fallback to sandbox** — Phase 6 already removed it; this phase preserves that invariant.

**Validation**
- Live `app.py` query into a city with a non-trivial airport fallback (e.g., a destination ≤200 mi from a hub). Confirm:
  - hotels are within ~30 mi of the dest airport's lat/lon (spot-check a few entries via Google Maps),
  - no hotels priced above the budget tier,
  - the lodging specialist's prompt now lists fewer / more relevant candidates.
- Eval path is untouched (uses `_sandbox_tool_context`, not `live.search_lodging_near`).

**Risks**
- `places_nearby` returns `price_level` for only ~60% of hotels; treat missing levels as "tier unknown — keep" rather than dropping. The over-fetch + sort handles this.
- Some destinations have no airport within 200 mi — `_resolve_with_fallback` raises, in which case we fall back to text search. Document this in the architecture invariants.

**Time.** ~1 hr.
